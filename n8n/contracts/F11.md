# Contrato F11 - Alertas fiscales (30/15/7 dias)

Flujo n8n: `EmWvCvSS3Y8Srwo4` (inactivo). Diario 7:30 America/Bogota. Endpoints **no existen aun**.

Reglas comunes de `/api/internal/*`: ver `F01.md`. Lista de tenants: `GET /api/internal/notification-targets?flow=F11` (definido en `F09.md`, seccion 0).

## 1. GET /api/internal/tenants/{tenant_id}/fiscal-deadlines

Vencimientos fiscales del tenant, **ya normalizados a fecha ISO**. Contexto `app.current_tenant_id = {tenant_id}`.

```json
{
  "tenant_id": "t-demo-1",
  "items": [
    { "kind": "certificado_digital", "label": "Certificado digital", "expires_on": "2026-10-25" },
    { "kind": "resolucion_dian", "label": "Resolucion DIAN", "expires_on": null },
    { "kind": "rango_numeracion", "label": "Rango de numeracion", "expires_on": "2026-10-19" }
  ]
}
```

- `kind`: `certificado_digital` | `resolucion_dian` | `rango_numeracion` (otros valores se muestran con `label`).
- `expires_on`: `YYYY-MM-DD` o `null` si el texto de origen no se puede interpretar. Con `null`, n8n avisa una vez "fecha no interpretable, revisala" (clave estable, no repite a diario).
- Para `rango_numeracion` (hoy `rango_hasta` es un numero, no una fecha) el backend decide: o devuelve la fecha estimada de agotamiento o `null`; fuera de ese caso el flujo no puede avisar por fecha.
- Sin datos personales, NIT ni numeros de certificado.

## Logica en n8n

- Umbrales: `jrpos_config.fiscal_alert_days` (`30,15,7`). Se avisa cuando `dias_restantes <= umbral`; el umbral "cruzado" es el menor que cumple. Vencido (`< 0`) tiene su propio umbral (-1).
- UN mensaje por tienda con todos los documentos en alerta. Severidad `alta` si algun documento esta a 7 dias o menos (o vencido), `info` en otro caso.
- Idempotencia (sondeo/reconciliacion): clave `F11:{tenant}:{kind}:{expires_on}:{umbral}` ordenadas y unidas con `|`. Si un dia no corre, el siguiente avisa igual; si nada cambio de umbral, I02 deduplica.
