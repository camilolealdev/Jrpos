## 0. GET /api/internal/notification-targets?flow=F09 (compartido por F09, F11, F12, F13, F14, F15)

Lista de tenants a los que ese flujo puede escribir. Corre con contexto de superadmin; devuelve **solo** ids y preferencias de envio, ningun dato de negocio, telefono ni correo. Solo incluye tenants activos (`status` distinto de `suspended`/`expired`) con opt-in vigente para el canal elegido.

```json
{
  "tenants": [
    { "tenant_id": "t-demo-1", "notify": { "opt_in": true, "channel": "whatsapp" } }
  ]
}
```

- Para `flow=F14` cada tenant incluye ademas `"accountant": { "configured": true, "opt_in": true }` (hay contador registrado y el dueno consintio enviarle el export). Sin ambos, el tenant no se incluye o n8n lo filtra.

## 1. GET /api/internal/tenants/{tenant_id}/low-stock

Productos del tenant con `stock <= min_stock` (solo los que tienen `min_stock` definido). Contexto `app.current_tenant_id = {tenant_id}`.

```json
{
  "tenant_id": "t-demo-1",
  "items": [
    { "product_id": "p1", "name": "Aceite 1L", "stock": 2, "min_stock": 10, "suggested_qty": 20, "supplier_id": "s1", "supplier_name": "Proveedor Uno", "unit_cost": 8000 }
  ]
}
```

- `suggested_qty`: cantidad sugerida (por ejemplo para llegar a 2 x min_stock); si es 0 o falta, n8n usa `max(1, min_stock - stock)`.
- `supplier_id`/`supplier_name` pueden ser `null` (n8n arma un grupo "Sin proveedor").
- Vacio: `{"tenant_id": "...", "items": []}`. Sin datos de personas.

## 2. POST /api/internal/tenants/{tenant_id}/purchase-orders/draft

Crea borradores de orden de compra, uno por proveedor. **Idempotente por `idempotency_key`**: repetir la llamada con la misma clave devuelve los mismos borradores con `created: false` y no crea otros.

Body:

```json
{
  "idempotency_key": "F09:t-demo-1:2026-10-13",
  "source": "n8n-F09",
  "orders": [
    { "supplier_id": "s1", "supplier_name": "Proveedor Uno", "lines": [ { "product_id": "p1", "qty": 20, "unit_cost": 8000 } ] }
  ]
}
```

Respuesta 200:

```json
{
  "tenant_id": "t-demo-1",
  "created": true,
  "orders": [ { "id": "oc-1", "supplier_name": "Proveedor Uno", "lines_count": 1, "total_estimate": 160000, "status": "borrador" } ]
}
```

Reglas: estado inicial **`borrador`** (nunca `enviada`); un borrador no notifica ni envia nada al proveedor. Si ya hay un borrador abierto para ese proveedor el backend decide si lo actualiza o lo reutiliza, pero siempre dentro del mismo tenant. `supplier_id: null` crea borrador sin proveedor para que el dueno lo asigne.

## Aprobacion del dueno

El dueno recibe UN mensaje por tienda y dia (clave `F09:{tenant}:{fecha}`) con enlace `{app_base_url}/compras` y aprueba el borrador **dentro de la app** (accion existente/por crear: `borrador -> enviada`). n8n nunca envia la OC al proveedor.

## Cambios de backend / BD requeridos

2. Estado `borrador` en `purchase_orders` (hoy nace `enviada`) y flujo de aprobacion `borrador -> enviada` en la app.
3. Columna/indice de idempotencia en `purchase_orders` (p. ej. `idempotency_key` unica por tenant) para el endpoint de borrador.
4. Endpoints 0, 1 y 2 y el router `/api/internal`.
5. `jrpos_config`: `backend_base_url`, `app_base_url`.
