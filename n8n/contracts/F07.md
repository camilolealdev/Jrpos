# Contrato F07 - Onboarding de tenant nuevo

Flujo n8n: `BuUrPXUXpPEWs6k3` (inactivo). Reglas comunes de auth, multi-tenant y datos personales: ver `F01.md`. El endpoint **no existe aun**.

## Entradas del flujo

1. Evento `tenant.registered` enrutado por I05 (Execute Workflow) con `event_id`, `type`, `tenant_id`, `data`. I05 ya valida token, ventana de 300 s y duplicados. F07 solo registra al tenant en la Data Table `jrpos_onboarding` (`tenant_id`, `registered_at`, `last_step`, `completed`).
2. Sondeo cada 2 h entre las 8 y las 19 h (Bogota) sobre los tenants con `completed = false`. El sondeo es la fuente de verdad: si el evento se pierde, hay que insertar el tenant en `jrpos_onboarding` o ampliar el contrato con un listado de tenants recientes (opcional, ver abajo).

Payload del evento (webhook backend -> I05):

```json
{
  "event_id": "evt-0001-ejemplo",
  "type": "tenant.registered",
  "tenant_id": "t-demo-1",
  "timestamp": 1791867000,
  "data": {}
}
```

`data` no debe incluir nombre, correo ni telefono del dueno.

## GET /api/internal/tenants/{tenant_id}/activity

Actividad real de **un solo tenant** (corre con `app.current_tenant_id = tenant_id`).

Respuesta 200:

```json
{
  "tenant_id": "t-demo-1",
  "status": "trial",
  "products_count": 0,
  "sales_count": 0,
  "last_sale_at": null,
  "opt_in": true,
  "channel": "whatsapp"
}
```

Reglas:

- `status`: `trial` | `active` | `expired` | `suspended`. F07 solo envia a `trial` y `active`.
- `products_count`: productos activos del tenant. `sales_count`: ventas completadas (no anuladas) desde el registro. `last_sale_at`: ISO 8601 o `null`.
- `opt_in` / `channel`: preferencias de `notification_prefs`. Sin opt-in no se envia nada y el paso no avanza.
- Solo contadores y banderas; sin nombres, telefonos ni correos.
- 404 si el tenant no existe; nunca revelar datos de otro tenant.

El mismo endpoint lo reutiliza F08 (reactivacion por inactividad) con el campo `last_sale_at`.

## Logica de pasos (en el flujo)

- Pasos D0, D1, D3, D7 desde `registered_at` (fecha Bogota). Se envia como maximo uno por ejecucion y por tenant, con ventana de gracia de 1 dia (pasos mas viejos se omiten y se avanza).
- D0 siempre; D1 solo si `products_count = 0`; D3 solo si `sales_count = 0`; D7 solo si `sales_count = 0`.
- Si `products_count > 0` y `sales_count > 0` el onboarding se marca completo y no se envian mas mensajes.
- Clave de idempotencia: `F07:<tenant_id>:<paso>` (estable por tenant y paso).

## Opcional recomendado

`GET /api/internal/tenants/onboarding?days=8` para que el sondeo recupere tenants registrados cuyo evento se perdio (reconciliacion, principio 2 del plan).
