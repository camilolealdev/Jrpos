# Contrato F15 - Asistencia (tardanzas del dia)

Flujo n8n: `GGstHvAskFiL0ExQ` (inactivo). Diario 10:30 America/Bogota. Endpoints **no existen aun**.

Reglas comunes de `/api/internal/*`: ver `F01.md`. Lista de tenants: `GET /api/internal/notification-targets?flow=F15` (definido en `F09.md`, seccion 0).

## 1. GET /api/internal/tenants/{tenant_id}/timeclock/late-today?grace_minutes=N

Entradas de hoy (fecha America/Bogota) con tardanza respecto al horario programado. Reutiliza la logica de `GET /api/timeclock/records`. Contexto `app.current_tenant_id = {tenant_id}`.

```json
{
  "tenant_id": "t-demo-1",
  "date": "2026-10-13",
  "grace_minutes": 10,
  "late": [
    { "employee_label": "Ana P.", "scheduled_start": "08:00", "clock_in": "08:25", "minutes_late": 25 }
  ]
}
```

- `grace_minutes`: tolerancia propia del tenant; `null` si no tiene (n8n usa `attendance_grace_minutes` de `jrpos_config`, hoy 10). n8n vuelve a filtrar `minutes_late > grace`.
- `employee_label`: nombre de pila + inicial. **Nunca** documento, telefono ni direccion.
- Empleados sin entrada registrada aun NO van en `late` (no se sabe si faltaron). Una futura ausencia seria un campo aparte.
- Sin tardanzas: `late: []` y n8n no envia nada.

## Logica en n8n

- UN mensaje por tienda y dia, solo si hubo tardanzas (maximo 10 nombres + "y N mas"). Clave `F15:{tenant}:{fecha}`; si el flujo corre dos veces el mismo dia no repite.
- Severidad `info`; solo dueno con opt-in.

## Cambios de backend / BD requeridos

1. Endpoint y `notification-targets`; router `/api/internal`.
2. **Horario esperado por empleado** (hora de entrada programada): si hoy no existe, hay que anadirlo; sin el no se calcula tardanza.
3. Tolerancia por tenant (opcional) en `notification_prefs`/ajustes de asistencia.
